# ENH: consider a limited-memory regularized quasi-Newton method for scipy.optimize.minimize

Hello, SciPy maintainers.
I'm Hiroki Hamaguchi, a doctoral student working in numerical optimization.

I greatly appreciate your work on SciPy, and I would like to discuss a possible addition to `scipy.optimize.minimize`.

(I previously mentioned this work in my presentation at [SciPyData 2026](https://scipydata.connpass.com/event/364718/) in Japan.)

This issue has two related motivations:

1. On some problems, the current L-BFGS-B implementation has a relatively large wall-clock cost per iteration.
2. Recent regularized quasi-Newton methods provide an alternative to the traditional line-search L-BFGS framework and may be faster or more robust on some problems.

I am therefore considering adding a new, Python-based, limited-memory regularized quasi-Newton method as an additional `minimize` method, but this plan is still tentative.

In this issue, I would like to ask whether this would be a reasonable direction for SciPy, and if so, whether you have any suggestions for the API or other design considerations.

## Motivations

### Per-iteration wall-clock cost

The first motivation is the current L-BFGS-B overhead.

SciPy's current implementation is written in [C](https://github.com/scipy/scipy/blob/main/scipy/optimize/src/lbfgsb.c), exposed through Python by [`minimize(method="L-BFGS-B")`](https://docs.scipy.org/doc/scipy/reference/optimize.minimize-lbfgsb.html).

[SciPy issue #23191](https://github.com/scipy/scipy/issues/23191) reports a performance regression between SciPy 1.14.1 and releases from 1.15 onward and discusses OpenBLAS thread behavior as an important possible cause.
The report also notes that limiting BLAS to one thread reduced but did not always remove the slowdown.
[A related downstream quadprog change](https://github.com/Jebel-Quant/quadprog/pull/71) addresses severe OpenBLAS oversubscription by limiting BLAS threads according to problem size.
These reports make it important to separate BLAS thread oversubscription from other sources of L-BFGS-B overhead.

Our reproduction notebook therefore compares SciPy 1.14.1, the SciPy version installed with the notebook, and the current SciPy `main` branch installed directly from GitHub.
It records the resolved version and Git revision for each run.
We have also conducted similar experiments on other PCs and on Linux, with qualitatively similar results.

The first experiment varies the iteration cap at fixed dimension.
For the environment represented in the saved figure, both Python implementations have lower end-to-end time than SciPy L-BFGS-B over the measured range.

![Zero-chain elapsed time versus iteration cap](https://raw.githubusercontent.com/HirokiHamaguchi/qnlab/main/doc/SciPy/experiment1_iteration_scaling.png)

The dimension sweeps show that this difference is not confined to a single problem or a narrow dimension range.
The Python methods are generally faster at small dimensions and again at large dimensions, including the measurements through $n = 10^6$.
The sharp change near $n = 10^4$ is retained deliberately because it is useful evidence of a size-dependent implementation effect.

| :---: | :---: |

The same large-dimension ordering appears with both tested L-BFGS memory values, so it is not specific to the default choice $m = 10$.

![Elapsed time for L-BFGS memory values 3 and 10](https://raw.githubusercontent.com/HirokiHamaguchi/qnlab/main/doc/SciPy/experiment4_lbfgs_memory_comparison.png)

Most importantly, the Python methods remain faster than SciPy at the larger dimensions when every BLAS pool is restricted to one thread.
Single-threading changes the location and size of the runtime transition, confirming that BLAS behavior matters, but it does not remove the remaining performance gap.
The known OpenBLAS oversubscription problem therefore does not appear sufficient to explain our measurements by itself.

![Default and single-threaded BLAS comparison](https://raw.githubusercontent.com/HirokiHamaguchi/qnlab/main/doc/SciPy/experiment5_blas_thread_comparison.png)

Because the compared solvers use the same Python objective and gradient callbacks, the residual gap is consistent with substantial overhead in the SciPy execution path, such as repeated Python--C transitions or dispatch of small BLAS operations.
This is an interpretation of the timing evidence rather than a completed low-level profile, and we do not claim that a C implementation is intrinsically slower than Python.
The SciPy 1.14.1 and current-`main` curves are included specifically to test whether the gap is associated with the post-1.14 implementation change or persists across implementations.

Further details are provided in [`notebooks/SciPy_issue.ipynb`](https://github.com/HirokiHamaguchi/qnlab/blob/main/notebooks/SciPy_issue.ipynb), a separate reproduction and diagnostic notebook.
The proposed method is not always faster than the current C implementation, but it is faster on many of the tested problems.
This is one of the motivations for proposing a new solver.

### Recent progress in quasi-Newton methods

The second motivation is recent progress in quasi-Newton methods.

The method we would like to propose is the noise-tolerant regularized quasi-Newton method (NTRQN) described in [our paper](https://arxiv.org/abs/2603.10642).

Before I explain the method, I would like to make clear that this proposal is not intended as self-promotion; I genuinely hope to contribute a useful solver to SciPy.
If the maintainers consider the method unsuitable, I will not pursue the proposal.

Although the particular combination is ours, many of its components build on developments from the numerical optimization literature over the past several decades:

- **Regularized quasi-Newton directions:** these methods compute a direction corresponding to $-(B_k+\mu_k I)^{-1}g_k$, following regularized Newton and limited-memory RQN work ([Ueda and Yamashita, 2014](https://doi.org/10.1007/s10589-014-9656-x); [Kanzow and Steck, 2023](https://doi.org/10.1007/s12532-023-00238-4)). Compared with line-search L-BFGS, this approach can be more robust or faster on some problems.
- **Curvature safeguards independent of Wolfe success:** damped BFGS and cautious selection of stored pairs maintain usable, spectrally bounded limited-memory approximations. This follows the cautious-update tradition ([Li and Fukushima, 2001](https://doi.org/10.1137/S1052623499354242)).
- **Optional modified secant information:** when function values are reliable, their interpolation information can improve the curvature model, following the modified-secant literature ([Zhang, Deng and Chen, 1999](https://doi.org/10.1023/A:1021898630001); [Yabe, Ogasawara and Yoshino, 2007](https://doi.org/10.1016/j.cam.2006.05.018)). Roughly speaking, this incorporates function-value interpolation, similar to that used in the Moré--Thuente line search in L-BFGS-B, into the quasi-Newton model update itself.
- **Use function values only when they are informative:** a relaxed, non-monotone Armijo test keeps ordinary quasi-Newton behavior when sufficient progress is observable. Otherwise, positive regularization is controlled by accumulated gradient norms, following the Objective-Function-Free Optimization (OFFO)/AdaGrad-Norm line of work ([Gratton, Jerad and Toint, 2024](https://doi.org/10.1080/10556788.2023.2296431), [Our paper](https://arxiv.org/abs/2603.10642)).

## Benchmarking

Below are some benchmark results illustrating the performance of the proposed method.

[CUTEst](https://doi.org/10.1007/s10589-014-9687-3) is a standard collection and testing environment for optimization problems.
We conducted tests on 220 unconstrained problems at 64-bit precision and 124 at 32-bit precision.
The limited-memory methods used $m=10$, and the maximum iteration count was 15,000.

The primary figures use Dolan--Moré [performance profiles](https://doi.org/10.1007/s101070100263).
For problem $p$ and solver $s$, the ratio is $r_{p,s}=\frac{n_{p,s}}{\min_{s'} n_{p,s'}}$, where $n_{p,s}$ is the number of oracle calls required to reach the stated gradient tolerance (and is infinite on failure).
At $\tau=1$, the height is the fraction of problems on which a solver was best.
At larger $\tau$, the height is the fraction solved within $\tau$ times the best solver's oracle count.
The final height therefore indicates robustness/coverage.

Of course, our method is not always the best because of the nature of non-convex optimization.
Still, within this benchmark, the proposed variants are competitive in oracle calls and per-iteration cost and solve a high fraction of the test problems.
Currently, our paper is under review, and these results may be improved or updated in the future.

## Box constraints (the "-B" in L-BFGS-B)

The method can be extended to box constraints, which would be necessary for a full L-BFGS-B replacement.

A working prototype, [`qnlab/solver/qn_ntrqnb.py`](https://github.com/HirokiHamaguchi/qnlab/blob/main/qnlab/solver/qn_ntrqnb.py), combines our method with a generalized Cauchy point and is able to solve box-constrained problems.

However, I do not currently plan to include this box-constrained variant.
It would add substantial implementation and maintenance cost, since an efficient implementation would likely require C code, as in the current L-BFGS-B implementation of generalized Cauchy points.
Box support could be considered later if there is sufficient user and maintainer interest.
